# 灵迈 LinkMai：面向中国法律工作的开源 AI 工作台

状态：产品设计建议稿，尚未进入本稿所述功能的实现与发布。

日期：2026-11-25。

已确认：品牌为「灵迈 LinkMai」；主要用户为国内律师、律所和企业法务；Web 与
Word 均在产品范围内；开源是产品路线的一部分。域名、支持邮箱、协议地址未确定。

本稿提出独立的产品定位、信息架构、首发场景和开源策略。此前的中文化变更作为基础
保留，不代表本稿中的产品能力已实现。当前仓库的大量未提交改动和并行官网工作不在
本稿中重新整理或覆盖。

## 1. 产品定位

**灵迈是可自托管、可扩展、能够交付可复核工作成果的中国法律 AI 工作台。**

面向律师、律所和企业法务，把材料阅读、规则审查、依据核对、文档修改和成果交付
放进同一个项目。让团队可以积累自己的审查标准、模板和任务流程，并选择是否将
经过整理的通用内容贡献给开源社区。

建议对外介绍：

> 灵迈 LinkMai 是面向中国律师与企业法务的开源 AI 工作台。围绕项目整理材料，
> 按团队标准审阅和起草文档，核对结论依据，并将修改交付到 Word。
> 支持自托管、自选模型与专业技能扩展。

建议产品副标题：**开源法律 AI 工作台**。

这一定义同时约束四件事：

1. 服务专业法律工作者，默认提供项目、团队标准、文档与交付流程。
2. 结果需要能够回到原文、来源和运行记录核查。
3. 组织可以控制部署、模型和知识来源。
4. 专业内容和扩展接口可供社区持续贡献，开源版本身可完成工作。

法律数据库覆盖规模、回答数量和多智能体数量不作为首版的核心卖点。

## 2. 从哪里切入

建议先服务：**有固定合同业务、愿意整理审查标准的小型法律团队与企业法务团队**。
这是首发获客与验证假设，不是已经验证的市场结论，也不排除个人律师使用。

| 用户 | 需要完成的工作 | 首版应交付的价值 |
| --- | --- | --- |
| 经办律师、法务 | 阅读、比对、修改合同，解释修改原因 | 可核对的审查发现、可接受/拒绝的修订稿 |
| 合伙人、法务负责人 | 统一立场，复核重要修改 | 可维护的团队标准、例外说明、复核记录 |
| 机构部署者 | 接入模型，控制资料访问和外发 | 可检查的模型配置、项目权限、可导出数据 |
| 社区贡献者 | 分享专业方法或扩展能力 | 有文档、有测试、有许可说明的贡献入口 |

**首条闭环：技术服务合同审阅 → 逐项确认 → Word 修订稿与审查意见表。**

选择它是为了让解析、审查、引用、修改、版本和导出共用一条可验收的路径。首批
场景包建议从保密协议、技术服务合同、采购/销售合同中选少量开始；具体先后顺序
应按实际试点团队的高频合同决定，避免同时承诺覆盖全部合同类型。

法律研究作为审查中的支撑能力同步设计。案件事实梳理与证据整理在第二条业务闭环
验证前不展开成完整诉讼管理系统。

## 3. 灵迈自己的产品原则

### 3.1 围绕交付物组织工作

对话是完成任务的入口。任务结束后，项目应留下可继续使用的成果：

- 原始材料、版本和提取覆盖情况；
- 用户确认的审查立场和交易事实；
- 审查发现、对应条款、判断依据和建议修改；
- 用户接受、拒绝及升级复核的决定；
- 修订稿、清洁稿、审查意见表等交付物；
- 运行所用模型、规则版本、来源快照和时间。

仅保存一段长回答不足以完成这条流程。清洁稿只应用用户已接受的修改；未处理的
发现必须在导出前可见，不能悄悄消失。

### 3.2 将中国法律工作的上下文做成产品输入

每次任务都能明确：任务类型、代表方、交易/争议背景、适用法域、相关地区、
时点和输出要求。已有项目事实优先复用；只询问会影响本次判断的缺项。

示例：技术服务合同中的「委托方 / 服务方」，不强行固定成「甲方 / 乙方」。
对方模板中的称谓、用户代表方与签约主体应分别确认。

法域属于具体事项。中国大陆是产品的默认服务环境，合同的明确适用法、用户指定
和跨境背景仍须单独处理。

### 3.3 把事实、专业判断和团队偏好分开

建议的发现类型：

| 类型 | 需要展示的依据 | 应避免的误导 |
| --- | --- | --- |
| 文档事实 | 精确原文、页码或段落定位 | 将提取失败说成条款不存在 |
| 法律适用问题 | 来源、版本、效力信息、适用前提 | 将模型常识冒充已核验法条 |
| 交易与执行风险 | 场景事实、条款关系、后果解释 | 将一方谈判诉求说成法定义务 |
| 团队标准差异 | 规则名称、版本、代表方和例外 | 将律所偏好说成统一法律结论 |
| 文字与一致性 | 冲突位置、定义及交叉引用 | 没有提示就改变法律含义 |

不使用没有校准依据的「法律准确率 98%」或统一可信分数。分别呈现可检查状态：
原文是否匹配、来源是否取得、版本是否核对、律师是否复核。

## 4. 信息架构：四个常用入口

建议主导航收敛为：

```text
工作台
项目
知识库
技能库

底部：工作空间切换 / 设置
```

| 入口 | 放什么 | 与现有仓库的关系 |
| --- | --- | --- |
| 工作台 | 最近任务、待复核成果、合同审阅/起草/研究等任务入口 | 重新组合 assistant 与 ide 的用户入口 |
| 项目 | 一个客户事项的事实、材料、任务、成果和成员 | 以 projects 为基础演进，保留权限和版本边界 |
| 知识库 | 团队参考资料、模板、条款库、已批准的专业资料 | 以 library 为基础，后续增加资料类型及来源管理 |
| 技能库 | 场景包、审查规则、工作流、模板、连接器 | 把 playbooks/workflows/模板的发现入口统一，执行类型仍区分 |

「批量审阅」放在工作台和项目内作为任务类型；「审查规则」与「工作流」进入
技能库。用户按工作目标开始，不需要先理解这些实现分类。

首版保留独立提问入口，但开始时明确使用「本次附件 / 当前项目 / 指定知识库」
中的哪些资料。新增模块只有具备真实可用能力才出现在主导航中。

项目内建议保持四个稳定区域：**概览、材料、任务、成果**。事实和成员放在项目
概览或详情中。项目可按合同、争议、研究分类，不急于建立覆盖全部法律业务的
统一复杂案件模型。

## 5. 核心工作台交互

### 5.1 一份合同的完整流程

```mermaid
flowchart LR
    A[上传合同与参考材料] --> B[确认代表方、范围与标准]
    B --> C[提取并检查文档覆盖]
    C --> D[生成有依据的审查发现]
    D --> E[逐项复核与调整修改]
    E --> F[修订稿、清洁稿、意见表]
    E --> G[建议更新团队标准]
    G --> H[负责人审核并发布新规则版本]
```

「建议更新团队标准」是显式操作。单次接受某项修改，不自动变成团队共识或
跨项目记忆；未复核的 AI 结论不自动进入知识库。

### 5.2 主界面

- 顶部：项目 / 文档 / 版本；代表方、审查标准；保存与导出。
- 左侧：材料和版本，必要时收起；不用占据主要阅读区域。
- 中间：合同正文、批注与修订，优先保证原文可读和精确定位。
- 右侧：问题列表或当前条款分析；展开单项后显示原文、依据、理由、修改及例外。
- 对话框：对选中段落追问、调整措辞、补充事实；不要求靠对话完成所有确认操作。

每项发现最少包含：**问题类型、原文、判断依据、影响、建议修改、处理状态**。
法律来源和团队标准分别显示，不能混在同一个「依据」标签下。

处理操作：接受修改、编辑后接受、保留原文、暂存待核查、提交负责人复核。
拒绝 AI 建议不是错误，不应被产品反复劝回。

示例（仅为交互演示，不代表具体合同的法律结论）：

```text
发现：验收安排不明确
类型：交易与执行风险 / 团队标准差异
原文：定位到本合同第六条
团队依据：技术服务合同 · 委托方立场 · 标准 v0.1
说明：当前条款未明确验收资料、期限与异议处理；结合交付安排确认是否补充。
法律依据：本项尚未核对外部法律来源
建议修改：展示可编辑条款草案
操作：编辑后接受 / 保留原文 / 待核查
```

### 5.3 Word 的角色

Web 适合材料、项目、批量任务和知识整理。Word 聚焦当前文档的阅读、审查、
改写和修订确认，两端共享任务、规则和来源，避免发展成两套互不相通的产品。

Word 每次修改都要绑定源文档与版本；原文发生变化时重新定位或请求复核，不能
直接把旧建议应用到相似文本。对格式无法保持的结果，导出前明确说明。

WPS 作为独立兼容性目标建立测试矩阵。Office.js 插件可在 Word 使用，不足以证明
WPS、各桌面版本及网页版本具有相同能力；在实测通过前不宣称全面兼容。

### 5.4 视觉与品牌表达

建议围绕长文阅读与专业复核建立自己的视觉语言：文档是页面中心，工具和 AI
建议退居辅助位置。浅色阅读底、清楚的正文层级、有限的强调色；批注、原文引用、
新增和删除各有稳定表达，不能只用颜色区分。

- 主工作区以文档与问题列表为主，避免大量装饰卡片和动画占据阅读空间。
- 功能名使用法律工作者熟悉的动作，例如「审阅合同」「起草文书」「核对依据」。
- 品牌、标志、图标与官网建立灵迈自己的资产，先核对上游素材来源和许可。
- 字体保证中文长文、数字、条款编号与中英混排的可读性；中文姓名和组织名可换行。
- 将现有视觉系统作为过渡基础。正式变更先更新 `docs/design-system.md` 和共享
  tokens，逐个完成主流程验收，不以散落的新颜色和局部样式形成第二套系统。

## 6. 法律资料与知识可信度

### 6.1 资料分三层

1. **事项材料**：合同、邮件、附件、项目事实。按项目授权，默认不跨项目检索。
2. **机构知识**：批准后的模板、条款、审查指引。指定知识集、权限及更新时间。
3. **外部法律来源**：可实际访问且具备适用使用条件的官方来源、用户已授权的
   数据库与连接器。来源授权与软件开源分别处理。

法律法规、司法解释、指导性案例、参考案例、其他裁判与团队文章分别建来源类型。
可以检索到、引文匹配、现行有效、适用于本事项，是四个不同的问题。

每条法律来源建议记录：标题、发布机关、来源地址、发布日期、生效/失效信息、
版本、取得时间、条文位置，以及可用的许可/使用约束。拿不到的字段显示未知。

### 6.2 首版可行路径

先把项目材料和团队资料用好，建立有版本的原文定位与来源展示。官方法律来源
可由用户提供原文或通过已验证的入口检索；专门的中国法数据库连接按可用性和
授权逐个接入，不宣称已经拥有全国全量法规、全部裁判或商业数据库能力。

涉及历史事项时应查相应时点的文本；外部链接变化后保留合法允许保存的来源信息
与校验记录。知识检索结果必须携带授权范围，不能仅在向量检索后才补权限过滤。

当前代码的文档搜索主要使用带权限和版本的文本检索；文档提取会报告扫描页覆盖
不完整，现有这条路径没有因此自动获得 OCR。中文扫描件 OCR、版面与表格还原需
单独评估、接入和测试，不能因为界面中文化就算已支持。

## 7. 开源产品与社区

### 7.1 开源交付承诺（建议）

可自托管的开源版本应能完成：项目与文档管理、审阅/起草任务、来源核对、规则和
技能的导入导出、基本多人权限、操作记录，以及 Word 使用和完整成果导出。
具体纳入首版的多人流程按现有代码逐项验收。

收费服务可围绕托管、部署升级、运维支持、培训与定制集成设计。任何付费扩展都
需先检查继承许可，不以更换文件夹或拆包作为规避许可证的依据。

### 7.2 内容生态比插件数量更重要

建议公开维护三个层次的资源：

| 资源 | 内容 | 发布门槛 |
| --- | --- | --- |
| 核心应用 | 文档、执行、权限、导出与客户端 | 测试、来源与安全审查 |
| 法律场景包 | 任务说明、规则、模板、示例和评测 | 清楚的适用范围、授权、负责人和已知局限 |
| 开发者接口 | 模型适配、资料源、Office 适配、工具扩展 | 文档、契约测试和最小权限声明 |

首期资源可先在同一仓库中组织；维护者与发布节奏真正独立后再拆仓库。

一个场景包至少包含：

```text
名称与说明
适用法域、事项类型、代表方、适用时点
输入要求、输出交付物
审查规则、工作步骤与模板（按需）
版本、维护者、来源与许可
示例材料与预期检查点
可调用工具和外部数据发送要求
已知限制、最近审阅与测试时间
```

场景包不能只有一段提示词。社区评审标签区分「作者贡献」「维护者审核」
「通过列明测试」等状态，不能以「官方审定」暗示法律正确性。

### 7.3 团队规则的版本化

现有 playbook 能手工编辑和从文档导入，也会保留审阅时的内容快照；它目前没有
独立发布版本的流程。建议在此基础上增加：草稿、负责人复核、发布、回滚。

运行时锁定规则发布版本和文档版本；新规则不改变旧审阅记录。规则修改需要展示
变更及受影响测试，不把原有自动保存直接当成组织统一标准发布。

### 7.4 社区贡献路径

贡献入口按不同能力设置：报告问题、补充中文界面、提供授权明确的场景包、
贡献合成样例/评测、扩展资料源与模型适配。通用内容进入公共仓库前，必须独立
选择导出和提交；客户项目、密钥、客户文档及机构内部规则默认不公开。

采用公开路线图、贡献指南和可重复的测试。发布包列明版本、变更、迁移与已知
局限；在早期按实际维护能力承诺兼容范围，不预先承诺长期支持期限。

## 8. 代码来源、许可与品牌

当前 checkout 的远端仍是 `open-legal-products/mike`，根许可证为 AGPL-3.0。
因此产品路线与品牌可以独立发展，代码出处和继承的许可义务仍须明确。

建议当前走 **基于 Mike 代码的公开衍生项目，建设独立产品与社区** 的路径：

- 在 README、LICENSE/NOTICE 和项目说明中保留依法需要的上游版权与来源；
- 对外明确灵迈独立维护的范围，以及与 Mike 无官方隶属或背书关系；
- 根据实际复制、修改和组合范围履行适用开源义务；AGPL 第 13 条涉及修改后程序
  的远程网络使用及对应源码提供；不能只换名称就改成 MIT/Apache；
- 模板、图片、图标、知识资料和场景包分别盘点来源与许可，不能把上游品牌资产
  当成自动获得授权的灵迈商标；
- 暂不设计依赖「核心代码私有化」或单方双重许可的收入模式。

若未来决定仅参考产品理念、另行独立实现，应单独核对代码与素材来源及改写边界。
大规模重写会占用交付资源，不建议作为当前独立产品定位的前置条件。

本节是产品与工程规划约束；具体发布和商业安排仍须结合完整权利来源核定。

## 9. 技术演进

保留现有 Next.js、Express、Postgres、对象存储与 Word 客户端的主体架构。
继续使用模块化单体和明确 facade，避免在业务未验证前拆出多个服务。

建议确立四个稳定的领域对象：

| 对象 | 关键责任 |
| --- | --- |
| 项目 | 事项范围、事实、成员与知识边界 |
| 文档版本 | 原件、提取文本、位置、修订与清理 |
| 任务运行 | 任务输入、模型、规则版本、来源和执行状态 |
| 交付物 | 结果文件、关联发现、人工处理状态与导出记录 |

按现有模块逐步补足这些语义，不要求先重建全部数据库。源文件生命周期继续由
documents 所属模块管理，跨领域交付由 application 协调。

新增或完善的契约：

- 来源契约：返回原文定位、版本、类型、授权范围及未知状态；
- 规则包契约：声明输入、规则、输出、能力权限、版本和评测；
- 文档编辑契约：同一修改能在 Web 与 Office 适配器间传递，保留失败与冲突状态；
- 运行契约：可停止、可重连、保留部分结果，不能把断线误报为任务已失败。

### 国内部署设计目标

- 默认安装和核心流程不强制依赖境外身份服务、字体、模型或对象存储。
- 提供经过测试的国内模型/企业网关配置示例，具体型号和能力跟随验证矩阵维护。
- 明确显示每项任务的模型目的地、外部检索与资料发送范围；本地部署不自动等于
  模型调用和全部数据都留在本地。
- 不默认向外部公共错误项目发送资料；日志与诊断的现有行为需单独审计后落实
  灵迈默认配置，不把此次设计文档当作已完成审计。
- 数据可导出、迁移和恢复；离线安装、备份和升级提供可重复操作的指南。

## 10. 首发范围与顺序

以下是建议的工作批次，按验收条件推进，不作为已承诺的交付日期。

### 第一批：完成一个专业任务

1. 工作台与项目导航收敛，任务入口改为合同审阅。
2. 以一个合同类型打通资料检查、代表方、审查标准与发现列表。
3. 逐项接受/拒绝/编辑建议，导出修订稿、清洁稿和意见表。
4. Web 与 Word 对同一项目、文档版本和规则形成一致认知。
5. 两家不同类型的试点团队使用真实授权或脱敏材料验收。

### 第二批：让团队与社区可以复用

1. 场景包规范及少量自编、来源明确的中文基础包。
2. 团队规则草稿、发布版本、运行快照和回滚。
3. 建立示例、回归评测、社区贡献和独立品牌的发布说明。
4. 国内模型、自托管与外部请求清单的部署验收。

### 第三批：扩展研究和争议业务

1. 接入实际可用且具备适当使用条件的中国法律资料源。
2. 专门处理时间版本、适用地域、来源冲突和法律研究交付物。
3. 验证案件事实时间线、证据目录、争议焦点三个成果，不直接铺开全部诉讼流程。
4. 依据真实需求增加 WPS、企业协作和知识系统连接。

## 11. 验收与取舍

北极星指标建议：**每周被专业用户复核并实际采用的交付任务数**。
每个任务只按预先定义的完成条件计数，避免将重复导出或简单聊天当成多个成果。

首期验证建议建立一个小规模、可审阅的样本集。数量可从约 30 份合成或已授权
脱敏文档开始，覆盖正文、表格、批注、定义、交叉引用、扫描页及历史版本。样本量
是工作计划，不应包装成对全部中国合同的准确率证明。

必须通过的检查：

- 每条修改能定位到确定的文档版本；定位失败时不静默应用。
- 未处理/未核实问题在交付前可见，提取不全不等于没有风险。
- 引用原文匹配与法律适用复核分别检查；不伪造来源。
- 不越权读取其他项目、个人空间或组织资料。
- 关键条款的人工采纳/拒绝原因可抽样回看；观察真实节省的复核时间。
- 使用新规则和不同模型运行同一批样本，能够对比漏报、误报、引用和格式问题。
- 干净环境可按文档部署，并知道哪些能力需要外部模型、网络与额外配置。

现阶段建议延后：全量商业法律数据库、自研基础模型、全法律领域自动办案、
完整客户管理/计费、面向公众的付费咨询、手机/微信登录与支付、插件交易市场。
这些功能应由后续试点证据决定优先级。

## 12. 对现有工程的动作建议

| 动作 | 内容 |
| --- | --- |
| 保留 | 中文化、输入法保护、文档版本、权限、任务续传、Word 修订、可导出数据 |
| 重组 | assistant/ide 的入口；把批量审阅和研究变为任务；统一技能发现入口 |
| 补足 | 项目事实、规则发布版本、交付物清单、来源分类与时点、中文场景包评测 |
| 重新审计 | 模型默认值、境外请求与遥测、官方法律资料源、上游模板及视觉素材 |
| 暂缓 | 架构大重写、应用/包的全局改名、与首条交付流程无关的集成 |

产品发布的独立身份应首先体现在 README、安装入口、文档、场景包、路线图、界面
任务组织和维护治理。内部 `@mike/*`、数据库对象或 API 路径的统一改名另开范围，
不与首发工作台混成一次高风险重构。

**建议下一份实现规格：合同审阅工作台。** 先画清上传、确认范围、定位问题、逐项
处理和导出五个状态，用一个可运行样例走通，再据此拆工程任务。
