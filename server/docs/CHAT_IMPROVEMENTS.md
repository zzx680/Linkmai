# 灵迈对话改进方案

日期：2026-11-14。范围：当前案件对话的反馈速度、消息一致性和客户端兼容性。代码实现不代表服务器及微信真机已经验收；发布统一遵循[部署指南](DEPLOYMENT.md)。

## 产品设计

用户发送消息后，先显示当前等待动效；收到首段正文后，逐步显示同一条回答。发送中的回答隐藏复制和时间，避免把尚未保存的内容表现为已完成结果。服务器成功提交用户消息与完整回复后，界面切换为正常消息并显示操作区。既有配色、间距和组件样式继续复用。

连接中断或模型输出不完整时，移除这次临时消息，恢复可重试状态；聊天页保留已有的草稿恢复逻辑。同一内容重试沿用 requestId，若前次已提交则返回原结果，避免因网络中断重复保存消息。案件信息冲突时刷新历史，下一次发送使用新 requestId。切换案件或退出登录后，迟到的正文与最终结果不能进入当前会话。

## 架构与本次实现

```text
微信输入
  → 已认证的案件对话接口
  → 当前案件上下文与原有系统提示词
  → 服务端调用 DeepSeek Chat Completions stream=true
  → SSE 正文增量 → 临时回答
  → 完整性校验 → 原有会话事务提交
  → done → 正式回答
```

本次借鉴 DeepSeek chat-demo 的流式交互思路，继续由灵迈服务端保管 API Key、校验案件权限并持久化对话。调用协议仍为 `/chat/completions`；没有增加新的模型提示词或改变普通聊天与案件事实确认之间的边界。

| 改进 | 实现 |
| --- | --- |
| 逐步显示正文 | 微信分块响应 + SSE；临时消息只在首段正文到达后创建 |
| 协议解析 | 分别解析 `event:` 与 `data:`；支持网络拆包、多事件合包、CRLF、中文和 emoji 跨字节分块 |
| 完整性 | DeepSeek 必须提供正常 `stop` 及 `[DONE]`，空回复、长度截断、协议错误和中途失败不提交 |
| 有界生成 | 流式整个模型调用最多 25 秒，普通调用最多 6.5 秒，均受 `DEEPSEEK_TIMEOUT_MS` 上限约束；流结束或失败后释放上游连接 |
| 数据一致性 | 完整推理后沿用既有快照校验、原子提交和 requestId 重放；正文增量不写数据库 |
| 异常恢复 | SSE 错误事件保留原有 409/503 语义；失败移除临时输出，重试复用 requestId |
| 隔离 | 每次正文更新都校验案件请求上下文；历史刷新不覆盖正在生成的回答 |
| 兼容 | 不支持微信分块请求的环境和 H5 使用普通接口；兼容旧后端返回的 JSON，以及网络层完整缓冲的 SSE |

### 客户端协议

接口：`POST /api/conversations/current/messages`，在既有请求体中增加 `stream: true`，并继续传入稳定的 `requestId`。未开启流式的调用保持 JSON 响应。

权限及参数验证在开始 SSE 前执行。开始流后 HTTP 状态为 200，业务错误通过 `error` 事件中的 `statusCode`、`code` 传递。

| 事件 | 数据 | 含义 |
| --- | --- | --- |
| `start` | `{"model":"deepseek"}` | 开始本次生成；不表示已生成正文 |
| `delta` | `{"delta":"正文片段"}` | 仅供临时展示 |
| `done` | `{"success":true,"data":{"message":"完整回答",…}}` | 会话已经提交，可使用最终结果更新界面 |
| `error` | `{"error":"可展示的错误","statusCode":503,"code":"MODEL_UNAVAILABLE"}` | 本次请求失败；未收到 done 不视为客户端成功 |

已提交请求重放直接返回 `delta` + `done`，不会再次调用模型。客户端断开后，当前服务端请求可能继续完成并提交；随后可用相同 requestId 重试取回结果。当前没有跨进程的生成中任务去重，因此两个客户端同时重试尚未提交的同一请求仍可能产生多次模型调用；原有事务只保证不重复写入。

## 验证与验收

自动回归覆盖：客户端消费实际后端事件格式、逐字节 UTF-8、断流和协议错误、整体生成时限、401 登录失效、409 冲突、普通 JSON 兼容、缓冲 SSE、会话重放、原子提交、临时消息替换及切换案件后的迟到响应。另需完成服务端构建、小程序类型检查、微信构建和原生聊天组件依赖检查。

staging 及真机验收场景：短回答、长 Markdown、连续追问、弱网中断后重试、首次连接延迟、输出中切换案件、页面返回和键盘遮挡。需核实 Nginx/网关没有缓存 SSE（响应已设置 `X-Accel-Buffering: no`），并观察首段正文延迟、完成耗时和中断率。真实 DeepSeek 调用、微信网络分块及滚动行为需要在目标环境验证，模拟测试不代替这些验收。

## 后续优先级建议

以下属于独立后续需求，不是本次已实现能力，也不改变既有案件 Harness 计划的完成状态。

1. 先补观测与评测：首段正文延迟、完成率、错误类型、实际 Token 用量，以及覆盖事故咨询场景的固定样本。日志只记录必要的运行元数据，避免案件原文与凭据进入日志。
2. 再做交互控制：停止生成、生成中请求去重、明确的重试入口和自动滚动跟随。需要定义中断内容是否保存、如何恢复与何时计费，再实现服务端取消与客户端控制。
3. 接入受控检索和来源：优先使用已有已审核法律资料与引用校验，通过明确授权的工具接口扩展。通用网页搜索、链接读取和模型生成的引用不能直接当作已核实法律依据。
4. 根据场景评测再决定模型分工、思考内容块或长上下文摘要。模型生成的思考文本不作为案件处理进度；文书分支、重新生成和材料权限需服从现有版本与审核机制。

当前不引入浏览器存 Key、会话仅存本地、通用工具自主执行或自动接受模型案件事实的模式。PDF/Word 导出、联网检索及模型微调均需独立设计与验收。
