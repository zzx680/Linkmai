- staging：`staging-api.linkmai.com` → 8100；production：`api.linkmai.com` → 8200。域名来自 Nginx 配置，未将配置存在解释为本次业务验收成功。
- 两环境 PostgreSQL 都在 loopback，SSL=false，数据库目标、用户和 JWT 不同。未输出数据库密码或 JWT。
- 两环境 OSS Bucket 相同；不是完整资源隔离，测试清理或权限变更不能影响正式材料。
- staging 的微信支付配置为 1 分；production 为 4990 分。模板的 staging 默认 provider 则是 disabled，文档区分模板与现有实例。
- 两个现有 Nginx 站点均未转发 `/review/`，模板也缺少该路径。
- 账号、目录权限与 PM2 管理身份沿用同日已完成的只读检查，不为整理文档改变权限。

## 后续整改结果（本地）

| 原问题 | 修复 | 生效边界 |
| --- | --- | --- |
| staging 掩盖失败 | 共用 deploy-release，每步失败停止，EXIT trap 清理自有候选 | 已回归，未远程执行 |
| production 无 staging 依赖 | checks → staging → production；同运行验收包及审批，正式持锁核对 staging 当前成功版本及进程 SHA | 需 staging Secrets、提交后启用 |
| 同 SHA 重跑破坏 release | ID 加 run_id/run_attempt，原子 mkdir 拒绝覆盖，源码独立且带校验和/SHA | 只重跑失败 job 可能复用旧输出，重复时重跑全流程 |
| staging 检查弱及竞态 | 配置/健康/功能/鉴权/版本 smoke，工作流串行，主机 flock 锁 | 人工使用同入口，业务真机仍人工 |
| 审核页未代理 | 两 Nginx 模板加 /review/，功能启用时 smoke 要求 200 | 线上未应用，须 nginx -t/reload/验收 |
| 上传无请求余量 | 两模板统一 51m | 线上未改，须边界验收 |
| 回滚猜第二新且不检查 | previous 或显式目标、自动 smoke、失败恢复，清理保留 current/previous | 不回滚数据库，仍需兼容性确认 |
| 高权限与共享资源 | 保持既有账号，不静默改服务器/OSS | 未解决，需后续受限发布入口与存储隔离 |

health 的 release 在进程启动时读取，避免仅切链接误报新版本。SHA 标记是溯源信息，不是抵御持 root 权限者的密码学证明。
